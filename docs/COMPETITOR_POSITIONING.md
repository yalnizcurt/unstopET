# Competitive positioning grounded in primary documentation

Reviewed 11 October 2026. Vendor capabilities below are **documented product claims**, not measured results from a shared test environment. No vendor was tested, scored or ranked. Features and licensing can change.

| Product | What its primary source describes | Relevant lesson for this prototype |
|---|---|---|
| Prisma AIRS | [Runtime Security overview](https://docs.paloaltonetworks.com/prisma-airs/ai-runtime-security/airs-vm-firewall/ai-runtime-security-overview) describes network/API interception, shared policies, prompt defenses, agent threats and DLP; some features depend on integration mode. | Show exactly which traffic is mediated and what a particular integration enforces. An SDK/API label alone cannot establish coverage of alternate tools. |
| Check Point AI Guardrails / Lakera | [Agent Behavior Defense](https://docs.lakera.ai/docs/agent-behavior-defense) separates prompt screening from dangerous tool deviations and deterministic tool allow/deny policy. [API overview](https://docs.lakera.ai/docs/api) exposes screening and detailed results. | Tool authorization is already a commercial capability; do not claim it is unique. Explain decision reasons and distinguish content risk from operation permissions. |
| SentinelOne Prompt Security | [Agentic AI product account](https://www.sentinelone.com/blog/prompt-security-for-agentic-ai/) describes agent/MCP discovery, governance and runtime interaction inspection. | A declared inventory of five registrations is useful but is not automatic enterprise discovery or MCP security. Keep disabled connectors visibly disabled. |
| Google Model Armor | [Official overview](https://docs.cloud.google.com/model-armor/overview) describes templates, confidence thresholds, prompt/response screening, sensitive-data protection, document limits, and inspect-only versus blocking modes. | Separate detector signals from enforcement. Track false positives, limits and inspect-only results; an independent model refusal does not prove a firewall block. |
| Cisco AI Defense | [Official data sheet](https://www.cisco.com/c/en/us/products/collateral/security/ai-defense/ai-defense-ds.pdf) describes visibility, validation and runtime protection with multiple traffic enforcement points. | A credible product should connect inventory, validation and actual runtime outcomes. Our fixed hosted workflows do not imply enterprise-wide visibility. |
| Zenity | [Platform description](https://zenity.io/platform) describes observability, posture, exposure, boundaries, agent identity, MCP security and detection/response across agent environments. | Investigation should connect source, agent, grant and effect. Our bounded incident timeline is an implementation demonstration, not equivalent ecosystem coverage. |

Our credible position is an **auditable, bounded agent-security prototype** for teams building a small set of hosted workflows. It demonstrates source inspection, server-controlled context, deterministic authorization and independent execution evidence in one product journey. The SDK example lets a separate application use that hosted boundary without owning a model credential. These are demonstrated integration choices, not claims that other products lack them.

The first-use detector results prevent a stronger security claim: 4/48 attacks detected and 6/16 benign signals, with no incremental classifier detections on the measured set. The familiar seven-category demonstrations and containment tests remain useful evidence for their specific scenarios. They are not evidence of superior commercial detection or universal protection.

Potential buyers are application/security teams that need a clear prototype of mediated agent execution and reviewable decisions. A pilot would validate their own workflows and data before introducing additional tools. Pricing, market share, purchase intent and production ROI are unmeasured. Development-stage free hosting and model quotas are deployment constraints, not a sustainable commercial cost model.

Near-term differentiation should be **transparent evidence**: preserve misses, false positives, provider failures, parser gaps, actual proposals and separately labelled forced-compromise probes. A future paid product would additionally need durable multi-tenant audit storage, enterprise identity, calibrated task-aware detection, broader supported integrations and independently reproduced evaluations. Those capabilities are not delivered by the present prototype.
